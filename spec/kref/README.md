# The kref grammar

This is the kref grammar that Kumiho DB and every Kumiho SDK share. The
conformance corpus [`vectors.json`](vectors.json) has 133 cases. It is
generated by [`tools/gen_vectors.py`](tools/gen_vectors.py). Each case records
three verdicts:

- what the **kumiho-db kernel** decides
- what the **original kumiho-server** decides
- what the **current Python SDK** (origin/main `a7f155e`) accepts and sends

The kernel and the corpus agree. The kumiho-db unit test
`kref_vectors_tests` checks every case against the real parser, using the copy
in `tests/data/kref-vectors.json`.

**Sources.** Unless a citation says otherwise, it refers to one of these:

| Short name | Revision | Files |
|---|---|---|
| kernel | kumiho-db `f013b04c` | `src/kernel/...` |
| adapter | kumiho-db `f013b04c` | `crates/kumiho-db-adapter/src/...` |
| server | kumiho-server `0e4906c` | `src/...` |
| SDK | this repo, `a7f155e` | `python/python/kumiho/...` |
| fix | branch `fix/kref-structured-parser-20261029` | as SDK, plus `parse_kref` and `KrefParts` in `kref.py` |

## 1. Who decides

1. **The kumiho-db kernel parser is the grammar.** Every kumiho-db read path parses through `parse_kref` (`src/kernel/commands/catalog/reads.rs:139-164`). This document describes that parser, and the corpus pins it.
2. **SDKs never become stricter than today.** An SDK must not refuse, before sending, anything that today's Python validator accepts. That validator is `_KREF_PATTERN` plus `validate_kref` (SDK `kref.py:70-123`). The original kumiho-server and that SDK work together in production, so anything the current SDK sends and the server accepts must still be sent.
3. **Where the kernel refuses and the SDK accepts, the SDK passes the string through.** The backend decides (`sdk_policy: "pass_through"`).
4. **SDKs may relax.** Where the kernel accepts and today's SDK refuses, an SDK may start accepting (`"sdk_may_relax"`). Examples are `?t=` and an artifact key before `r`. This is optional.
5. **Splitting a kref into GetItem parts follows the kernel grammar** (§5). Wherever that changes a request the SDK sends today, the change has to be proved server-equivalent (§6).

## 2. Grammar

```ebnf
kref        = "kref://" base [ "?" query ] ;             (* no '#', no '%' anywhere *)
base        = segment { "/" segment } ;                  (* 1..=1024 UTF-8 bytes, 1..=32 segments,
                                                            no ".." substring, no control char *)
segment     = word { word | "." | "-" } ;                (* ^\w[\w.-]*$, Unicode \w *)
word        = ? Rust regex Unicode \w: Alphabetic | Mark | Decimal_Number
                | Connector_Punctuation | Join_Control ? ;

project_kref   = segment ;                               (* exactly 1 segment *)
space_kref     = segment "/" segment { "/" segment } ;   (* >= 2 segments: project, spaces *)
item_kref      = segment "/" segment "/" { segment "/" } leaf ;  (* >= 3 segments *)
root_item_kref = segment "/" leaf ;                      (* exactly 2: item directly under the project *)
leaf           = name "." kind ;                         (* split at the LAST '.' of the last segment *)
name           = ? non-empty, may contain '.' ? ;
kind           = ? non-empty, never contains '.' ? ;
bundle_kref    = (item_kref | root_item_kref) with kind = "bundle" ;

query       = pair { "&" pair } ;                        (* each key at most once, any order *)
pair        = "r=" ( revnum | "latest" ) | "t=" tag | "a=" artifact ;
revnum      = nonzero_digit { ascii_digit } ;            (* 1 ..= 18446744073709551615 *)
tag         = ? 1..=1024 UTF-8 bytes, no '"', no '\', no control char,
                and (because the query is not decoded) no '&', '#', '%' ? ;
artifact    = ? 1..=256 bytes of ASCII [A-Za-z0-9._-] ? ;
```

### Constraints the EBNF cannot express

1. The scheme is exactly the bytes `kref://` (`src/kernel/model/catalog.rs:148`, `:174-176`). `KREF://`, `kumiho://` and `kref:/` are refused.
2. The base is everything between the scheme and the **first** `?`, kept byte for byte (`catalog.rs:166-170`, `:177-180`). Nothing is normalized: no case folding, no NFC, no percent decoding.
3. A `#` or `%` anywhere after the scheme refuses the kref (`catalog.rs:181-187`). There is no fragment and no percent escape.
4. The base must pass `valid_kref_path` (`src/kernel/keys/catalog_components.rs:182-205`):
   - 1..=1024 UTF-8 bytes. This is `MAX_KREF_BYTES` (`:24`), from owner decision KREF-1K.
   - 1..=32 `/`-separated segments. This is `MAX_KREF_SEGMENTS` (`:26`).
   - No `..` substring and no Unicode control character (`:183`; `has_control` is in `tag_rules.rs:18-20`).
   - Every segment matches `^\w[\w.-]*$` (`:173-175`).

   It follows that empty segments, a leading `/`, a trailing `/`, `.` and `..` segments, and segments that start with `-` or `.` are all refused.
5. The limits apply to the **base only**. The scheme and the query are not counted, so a 1,024-byte base with a 1,024-byte tag is valid (vector `limit-query-not-counted`).
6. Item and root-item paths need the last segment's **last** `.` to have a non-empty name before it and a non-empty kind after it (`catalog_components.rs:200-203`, `rsplit_once('.')`). A kind therefore never contains a dot. `kref://p/s/x.tar.gz` is item `x.tar` of kind `gz` (vector `kind-with-dot-unrepresentable`). The kumiho-db GetItem adapter refuses a request whose kind contains `.` or whose name contains `/`, with `INVALID_ARGUMENT "the kref names no item"` (adapter `convert/item_reads.rs:69-96`).
7. The namespace counts are in `catalog_components.rs:187-194`:
   - project: exactly 1 segment
   - space: at least 2
   - item ("Base"): at least 3
   - project-root item ("RootBase"): exactly 2

   Items and bundles share one namespace (`:131-137`).
8. Query rules (`catalog.rs:202-240`):
   - Each `&`-separated pair is split at its **first** `=`. So `t=a=b` is the tag `a=b`.
   - Only the keys `r`, `t` and `a` exist. They are case-sensitive and each may appear at most once, in any order.
   - `r` and `t` together are refused.
   - `r=latest` means the tag `latest`, not a number (`:226`).
   - A revision number is ASCII digits only, with no sign and no leading zero, and is ≥ 1 and fits in u64 (`:243-249`).
   - A tag must satisfy `valid_tag` (`tag_rules.rs:27-32`).
   - `a` needs `r` or `t`, and must satisfy `valid_artifact_name` (`catalog_components.rs:215-221`).
   - An empty query (`kref://…?`), an empty pair (from `&&` or a leading or trailing `&`) and a pair with no `=` are all refused.
9. **`time` is not a kref key.** `?time=` and `?tag=` are refused as unknown keys. The legacy `?v=` is refused the same way. The as-of time travels in `ResolveKrefRequest.time` and `ResolveLocationRequest.time`. kumiho-db accepts two forms there and refuses everything else (adapter `convert/resolve.rs:109-134`):
   - RFC 3339 with an explicit offset, detected by `T` or `t` at byte 10
   - exactly 12 ASCII digits `YYYYMMDDHHMM`, read as UTC at second :59

   On the wire, a separate `tag` field and a `t=` in the kref must agree (`convert/resolve.rs:136-175`). The corpus field `time` is therefore always `null`.

## 3. Shapes and the ambiguity of dotted names

A base may satisfy several namespace rules. The corpus field `shapes` lists every one it satisfies, in the order the parser and the resolver try them: `root_item`, `item`, `space`, `project` (`reads.rs:145-150`; resolver `src/kernel/commands/catalog/resolve.rs:165-184`). The resolver takes the first namespace with a binding.

Two cases follow:

- **Every item kref is also a valid space path**, because `x.k` is a valid space segment. If an item `x` of kind `k` exists in `p/s`, it shadows a space `p/s/x.k`.
- **A two-segment base whose last segment holds a dot is ambiguous.** `kref://p/s.v1` is either the project-root item `s` of kind `v1` or the space `p/s.v1`. The resolver tries the root item first (`resolve.rs:177-181`). On storage levels where project-root items cannot exist, it skips that namespace.

The corpus's item fields (`project`, `space_path`, `item_name`, `kind`, `is_project_root_item`, `get_item_tuple`) describe the **first** shape. A base whose first shape is `space` or `project` has `item_name`, `kind` and `get_item_tuple` set to `null`. Examples:

- `kref://p/s/x` (no dot) is a space.
- `kref://p/s/x.` (empty kind) is a space too, because `x.` is a valid segment.

The parser accepts a selector on a project or space: `kref://p?r=1` parses. The resolver then refuses it with `Invalid("a revision selector names an item or bundle")` (`resolve.rs:196-198`). The corpus is a parse-level corpus.

## 4. Parse order and which error wins

`parse_kref` (`reads.rs:139-164`) runs `KrefQuery::parse` (`catalog.rs:173-200`) once for each namespace, in shape order, and returns the first success. If every namespace fails, it returns one of two errors:

- the error of the **first namespace whose path rule the base satisfies**, so a bad query on a good base reports the query problem
- otherwise, the error of the last namespace tried

Because the scheme and `#`/`%` checks come before the path check, and the query rules do not depend on the namespace, the effective precedence is:

| order | `error_class` | exact kernel message (`EngineError::Invalid`) | source |
|---|---|---|---|
| 1 | `scheme` | `a kref starts with kref://` | `catalog.rs:174-176` |
| 2 | `tag_reserved_char` | `tag selector cannot contain '&', '#' or '%'` | `catalog.rs:153-162`, `:181-184`, `:207-213` |
| 2 | `fragment_or_percent` | `a kref has no fragment and no percent escape` | `catalog.rs:181-187` |
| 3 | `path` | `invalid kref path` | `catalog.rs:188-190` |
| 4 | `query_pair` | `a kref query pair is key=value` | `catalog.rs:207-213` |
| 4 | `unknown_key` | `unknown kref query key` | `catalog.rs:214-219` |
| 4 | `duplicate_key` | `duplicate kref query key` | `catalog.rs:220-222` |
| 5 | `r_and_t` | `a kref names r or t, not both` | `catalog.rs:225` |
| 5 | `revision_number` | `a revision number is a positive integer` | `catalog.rs:227`, `:243-249` |
| 5 | `tag` | `invalid tag` | `catalog.rs:228-229` |
| 6 | `artifact` | `an artifact needs a revision selector and a valid name` | `catalog.rs:232-236` |

**Order 2.** If a `#` or `%` sits inside a `t=` value, the tag message wins. Otherwise the fragment message applies.

**Order 4.** Pairs are checked left to right, and the first bad pair decides which of these errors is reported. A pair without `=` that follows a `t=` pair reports the tag message instead, because that is what a tag holding `&` leaves behind.

**Write rules are separate.** Creating a project, space, item or bundle runs extra checks on the new name (`src/kernel/keys/kref_write_rules.rs`):

- the name must already be in NFC
- it must contain no default-ignorable code point; this includes U+200C and U+200D unless the operator allows join controls

These checks apply only to creation. Reads keep the grammar above, so every stored name stays addressable. That is why `unicode-nfd-read` and `unicode-zwj-read` parse as valid.

## 5. From a kref to a GetItem request

The GetItem request `(parent_path, item_name, kind)` for an item kref is the corpus field `get_item_tuple`. It is built like this:

- `parent_path` = `"/"` + everything before the **last** `/` of the base (the project and any nested spaces)
- `item_name` = the last segment up to its **last** `.`
- `kind` = the text after that `.`

The query is dropped. For a project-root item, `parent_path` is `/project`.

This is the kernel's split (`catalog_components.rs:200-203`). kumiho-server uses the same split where it parses item krefs itself: `parse_item_kref`, `src/revision.rs:547-568`, uses `rsplit_once('/')` and `rfind('.')`.

SDKs must not hand-split krefs with `split('/', 1)` or `split('.', 1)`. They should use one parser that implements this section and passes the corpus.

### Strings without `://`

The textual split starts after the first `://`. A string without one is its own path, and the SDKs keep what their path accessor returned at `a7f155e`: Python and C++ return the whole string, query included, while Go and Rust still cut it at the first `?`. No validated kref lacks the scheme (`no-scheme` is refused by every validator), so this only decides what the path accessors return for an unvalidated string. The corpus has no such input, and each SDK's own tests pin its behavior.

## 6. Compatibility with kumiho-server and the current SDK

### What kumiho-server enforces

kumiho-server enforces less, and in fewer places:

- **Its kref regex** (`src/utils.rs:60-63`, `is_valid_kref` `:67-79`) is `^kref://\w[\w.-]*(/\w[\w.-]*)*(\?r=\d+(&a=[a-zA-Z0-9._-]+)?)?$`, plus a `..` check and a control-character check. It has no length or segment limit and no namespace counts, and it allows only `?r=N[&a=…]`. Its `\d` is Unicode, so it accepts `?r=0`, `?r=01`, `?r=٣`, and numbers beyond u64.
- **It applies the regex only where it builds a kref:** `create_item` (`src/item.rs:180-191`) and batch rows (`src/revision.rs:547-568`). `create_bundle` builds its kref without validating it (`src/bundle.rs:122-127`). `create_item` checks only that `item_name` and `kind` are non-empty and that the kind is not reserved. So a kind with a dot (`x` + `tar.gz`) or a name with a `/` can be stored. The stored `item_name` and `kind` properties, not a split of the kref, are what that server considers authoritative.
- **Its read RPCs do not validate.** They match stored strings exactly:
  - `get_item` (`src/item.rs:436-456`) builds `kref://{normalize_space_path(parent_path) minus leading '/'}/{item_name}.{kind}` and matches `p.kref`. `normalize_space_path` is `src/item.rs:14-31`.
  - `get_revision` (`src/revision.rs:1609-1665`) chooses its revision path when the string contains `?r=`, after stripping `&a=…` (`utils.rs:96-101`).
  - `resolve_location` (`src/revision.rs:2867-2960`) reads `r`, `t`, `tag` and `time` out of the query, silently ignores unknown keys and an unparsable `r`, and lets the request's `tag` and `time` fields win.
  - `resolve_kref` (`src/revision.rs:2611-`) takes the kref as a base and reads `tag` and `time` from request fields. A `time` containing `T` is ISO; otherwise one of 12 or more characters is read as `YYYYMMDDHHMM`, without a digit check.

So `server_accepts` in the corpus is the regex verdict. The read RPCs answer "not found" rather than "invalid".

### What the current Python SDK does

- **It validates** with `_KREF_PATTERN` (`kref.py:70-76`) and `validate_kref` (`:80-123`):
  - `..` anywhere is refused, including in the query
  - characters below U+0020 and U+007F are refused
  - the path is `\w[\w.-]*` segments, or the legacy `/`-prefixed form `kref:///space`
  - the query is only `?r=\d+(&a=…)?`

  Python's `\w` has no combining marks and no join controls, so the SDK refuses NFD and ZWJ names that the kernel and server read.
- **`get_item_by_kref`** (`client.py:915-936`) and **`get_item_from_revision`** (`:1332-1355`) split at the **first** `/` and the **first** `.`.
- **`get_bundle_by_kref`** (`:938-981`) does the same, and then re-fetches with `item_name` = the text before the first `.` and `kind="bundle"`.
- **`get_revision`** (`:1284-1330`) does not validate. It moves `t=`, `tag=` and `time=` into `ResolveKref` fields, and the time must match `^\d{12}$`. Values are cut at the second `=`.
- **`resolve`** (`:1859-1888`) sends the **whole** kref, query included, to `ResolveLocation`, along with the tag and time it copied out.

### Current SDK requests that kumiho-db answers differently from kumiho-server

None of these depend on the split fix. They are recorded in `sdk_current_request`.

- **`resolve()` with `?time=…` or `?tag=…`.**
  - kumiho-server reads those keys only when the request field is empty, and the SDK fills the field with the same value (`src/revision.rs:2937-2960`). So the server answers. Its `time` filter is not implemented there: the `Time travel TODO` at `:2984` means it resolves the latest revision.
  - kumiho-db's adapter passes the kref unchanged to the kernel, which refuses `unknown kref query key`. The adapter re-adds only `t=` (`convert/resolve.rs:136-175`, `:225-242`).
  - Stripping `time=` and `tag=` from the kref before sending would not change what the server resolves, because the server takes them from the fields first. Either the adapter tolerates these keys, or every SDK strips them. Under rule 2, the SDK must still send the request.
- **`get_revision()` with a number the kernel refuses** (`?r=0`, `?r=01`, `?r=٣`, beyond u64): the server answers NOT_FOUND and kumiho-db answers INVALID_ARGUMENT. Both are failures.
- **`get_revision()` with `?t=a=b`:** the SDK sends the tag `a`, but the kernel grammar reads the tag `a=b`.
- **Legacy `kref:///…`:** kumiho-db refuses it (`legacy-leading-slash-*`). The server normalizes the GetItem form (`item.rs:14-31`).

### Equivalence of the split fix

Proof:

1. kumiho-server's GetItem selects its node by exactly one string, `p.kref`, built as described above (`src/item.rs:443-456`).
2. No other request field takes part.
3. Therefore two requests reach the same node if and only if they build the same string.

The generator computes that string for the current and the fixed request of every case and records it in `server_equivalent_old_new`. **For `get_item_by_kref`, every case is server-equivalent.** Consider the old request for `kref://p/a/b/c/x.k`, which is `("/p", "a/b/c/x", "k")`. It builds the same `kref://p/a/b/c/x.k` as the new `("/p/a/b/c", "x", "k")`, because the server joins the strings back together. `get_item_from_revision` runs the same split on the item kref the server returned, so the same proof covers it.

kumiho-db refuses the old request for nested items, dotted names and dotted spaces (`kumiho_db_old: "INVALID_ARGUMENT: the kref names no item"`) and accepts the new one.

### Item krefs only a server can return

The corpus holds krefs the SDK validators accept, and no validator accepts a space segment that ends in whitespace or an empty segment. An item kref that the server returns is not validated by the Python client when it reads it (`get_item_from_revision` splits `revision.item_kref`), so it can still be one: `kref://p/s /x.k` or `kref://p//x.k`. Splitting these at the last `/` is not server-equivalent. `normalize_space_path` (`item.rs:14-31`) trims whitespace and `/` from the parent, so `("/p/s ", "x", "k")` is looked up as `kref://p/s/x.k` and `("/p/", "x", "k")` as `kref://p/x.k`. Those are different nodes from the ones `a7f155e`'s `("/p", "s /x", "k")` and `("/p", "/x", "k")` reached.

**Rule.** An SDK that splits an item kref it has not validated sends the §5 split only when kumiho-server builds the same key for it as for `a7f155e`'s request. Otherwise it sends `a7f155e`'s shape: the project as the parent, and everything after it up to the last `.` as the name. Python implements this in `KrefParts.get_item_request()`; `get_item_tuple()` stays the pure §5 split that the corpus records. The legacy `kref:///s/x.k` passes the test, because `("//s", "x", "k")` and `("/", "s/x", "k")` build the same key.

The other SDKs meet the rule in their own way, and each has a test for it:

- **Rust and Go** validate every item kref before they split it, as at `a7f155e`, so such a kref is refused before any request.
- **C++** does not validate. At `a7f155e` it already split at the last `/` and sent every segment as it was, so its request is unchanged.
- **Dart** has not changed since `a7f155e`: it drops empty segments and sends the rest as they are.

### Flagged cases

1. **`get_bundle_by_kref` re-fetch is NOT equivalent for `bundle-dotted-name` and `bundle-in-dotted-space`.** For `kref://p/s/my.set.bundle` the current SDK re-fetches `kref://p/s/my.bundle`. For `kref://p/s.v1/set.bundle` it re-fetches `kref://p/s.bundle`. Those are different nodes from the one it first looked up. Today's call therefore returns a different bundle, if one exists under that name, or NOT_FOUND. The fix fetches the bundle the kref names. This changes which node the server returns, so the owner must decide whether it ships.
2. **Root-level dotted names change their request bytes** (`root-item-dotted-name`: `("/p","my","file.k")` → `("/p","my.file","k")`). The two requests are server-equivalent, but the old one is refused by kumiho-db, which refuses a `kind` containing `.`. **Byte identity and kumiho-db compatibility cannot both hold for this case.** Every root-level item without a dot in its name keeps byte-identical requests: `root-item`, `root-item-revision`, `bundle-root`, `two-segment-dotted-ambiguous` and `legacy-leading-slash-root-item`.
3. **Legacy `kref:///s/x.k` changes its request bytes** (`("/","s/x","k")` → `("//s","x","k")`). The server normalizes both to `kref://s/x.k` (`item.rs:14-31`), so they are equivalent. kumiho-db refuses both. A fix that must keep these bytes can special-case a path that starts with `/`.
4. **One case where the fix is stricter than today: `dotted-space-leaf-without-dot`.** Validation is unchanged on the fix branch. Both splits raise `ValueError` on the same inputs, with one exception: a last segment with no dot under a dotted space or project, such as `kref://p/s.v1/x`.
   - The current SDK splits at the first `.` and sends `GetItem("/p", "s", "v1/x")`.
   - The fix raises before sending.
   - The server builds `kref://p/s.v1/x` and matches it. That can only find an item created with the kind `v1/x`, which `create_item` allows because the regex accepts the joined kref. In every other case the answer is NOT_FOUND.
   - The kernel reads this kref as the space `p/s.v1/x`.

   If the owner requires zero new client-side refusals, the fix must keep sending this request instead of raising.

   The owner kept the refusal (2026-10-29). It has one more visible consequence: `Project.get_item(name, kind)` builds `kref://project/name.kind`, so a kind that contains `/` (for example `image/png`) gives the leaf `png`, which has no `.`, and is refused before sending. A kind containing `/` is not valid.

### Public accessors whose output changes (fix branch)

Only the kind accessor changes (`Kref.get_kind()`, `Kref::kind()`, `Kref.Kind()`, `Kref::getKind()`), and only for dotted item names. For example, `kref://p/s/my.file.v2.k` changed from `file.v2.k` to `k`. The corpus records each change in `sdk_fix_accessor_changes`. Owner decision 3 (2026-10-29) keeps this.

- **Python:** no production caller of `get_kind()` or `get_item_name()` in the SDK, kumiho-cli, the MCP server, kumiho-memory or kumiho-plugins. Only `tests/test_kref.py` and docstrings use them.
- **Rust:** `Kref::kind()` gates event classification in the dashboard (`dashboard/src/live.rs:102`). Today, events for dotted names are misclassified there.
- **Go:** `Kref.Kind()` has test callers only.
- **C++:** one more accessor changes. `Kref::getItemName()` and its alias `getProductName()` split at the first `.` at `a7f155e` as well, so `my.file.v2.k` was item `my`. They now split at the last `.` like `getKind()`, and the owner kept that too. The SDK has no caller of either (`Item::getItemName()` and `Item::getKind()` read the response, not the kref).

For an item that kumiho-server stored with a dotted kind, `get_kind()` matched the stored `kind` before the fix and does not after it. Neither split can be right for both a dotted name and a dotted kind, because that server's krefs do not determine the pair. The kernel grammar decides in favour of the dotted name.

## 7. The corpus

Each case in `vectors.json` has these fields:

| Field | Meaning |
|---|---|
| `id`, `category`, `input` | – |
| `valid`, `error_class`, `kernel_error` | the kernel's verdict and its exact message |
| `base` | – |
| `shapes` | – |
| `project`, `space_path`, `item_name`, `kind`, `is_project_root_item` | the first shape (§3) |
| `revision`, `tag`, `artifact` | – |
| `time` | always `null` |
| `get_item_tuple` | – |
| `server_accepts` | – |
| `sdk_current_accepts`, `sdk_policy` | – |
| `sdk_current_request` | `get_item_by_kref`, the `get_bundle_by_kref` re-fetch, `get_revision`, `resolve` |
| `sdk_fix_request` | – |
| `server_equivalent_old_new` | – |
| `sdk_current_accessors`, `sdk_fix_accessor_changes` | – |
| `note` | – |

The top-level `fields` object in the file repeats these definitions.

### How to use it

**SDK conformance.** An SDK's parser must agree with the following fields for every case its own validator accepts:

- `valid`
- `project`, `space_path`, `item_name`, `kind`, `is_project_root_item`
- `revision`, `tag`, `artifact`
- `get_item_tuple`

An SDK's validator must accept at least every case where `sdk_current_accepts` is true (§1).

**Regenerating.** Run `python spec/kref/tools/gen_vectors.py` from the repository root. It does four things:

- It executes the snapshotted `kref.py` of `a7f155e` (`tools/snapshots/`) and the working tree's `python/python/kumiho/kref.py`, so the corpus records what the Python SDK being tested sends and there is no second copy to go stale.
- It ports the kernel, server and adapter rules it cites.
- It asserts the hand-written `valid` and `error_class` of every case.
- It refuses to write the corpus if they disagree.

After regenerating, copy the corpus to kumiho-db's `tests/data/kref-vectors.json` and run `cargo test --lib kref_vectors`.
